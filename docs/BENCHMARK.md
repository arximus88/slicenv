# Порівняльний бенч: Slicenv ↔ Bambu Studio ↔ OrcaSlicer

Скільки CPU, пам’яті й GPU бере Slicenv на холодному старті, при відкритті файлів, нарізці
й роботі з камерою, і як це виглядає поруч з оригінальними Bambu Studio та OrcaSlicer.

- Прогін: 2026-11-08, arx-pc: Ryzen 7 7840HS (16 потоків), Radeon 780M (RADV / radeonsi),
  64 ГБ, CachyOS, ядро 7.3.1, GNOME 51.
- Сирі дані (кожен прогін, ряд CPU/RSS/PSS/GPU кожні 0,5 с, події-маркери, підсумок
  «медіана / min / max / n») у репозиторій не входять — `tools/bench/compare.py` пише їх
  у `bench/compare-<дата>.json`.
- Відтворення: `tools/bench/compare.sh` (обгортка) → `tools/bench/compare.py` (вимір) →
  `tools/bench/compare_table.py` (таблиці нижче).

## Методика

**Дисплей.** Кожен GUI — X11-клієнт приватного `mutter --headless --virtual-monitor 1920x1080`
(Xwayland із апаратним GL/Vulkan на 780M). Xvfb не підходить: у ньому GL оригіналів іде через
llvmpipe на CPU, а Slicenv малює Vulkan на GPU — порівняння CPU/GPU було б нечесним. Керування
вводом — `xdotool` (XTEST у Xwayland). Усі застосунки — X11-клієнти (Slicenv теж, без
`WAYLAND_DISPLAY`): так один інструмент вводу працює для всіх, але це не той шлях презентації,
що в Slicenv на робочому столі (там нативний Wayland).

**Ізоляція.** Для кожного застосунку — власні тимчасові `HOME`, `XDG_CONFIG_HOME`,
`XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_STATE_HOME`. Справжні `~/.config/{slicenv,BambuStudio,
OrcaSlicer}` і `~/.local/share/slicenv` не відкриваються (рушії звідти — лише бінарники для
читання); скрипт порівнює mtime цих тек до й після (у прогоні — без змін). Оригіналам кладеться
мінімальний конфіг (`firstguide.finish`, ті самі пресети, `backup_switch=false`), щоб не було
майстра першого запуску; Slicenv — `preferences.json` (`wizard_done`, `open_3mf=project`,
MCP вимкнено) і `engines.json` з потрібним рушієм; `SLICENV_CLOUD_OFF=1`. Хмари, входу,
принтерів немає. Процеси зупиняються за PID власного дерева. Резервні копії, які оригінали
пишуть у `/tmp/bamboo_model`, `/tmp/orcaslicer_model` (і GUI, і CLI рушія — тобто й кожна
нарізка в Slicenv лишає там копію проєкту), видаляються лише для своїх PID.

**D-Bus.** Приватна сесійна шина без каталогів служб: будь-яка активація (gvfs-монітори томів,
at-spi, портали) одразу повертає помилку. Інакше GIO/GTK оригіналів чекали таймаути активації
по 18–25 с — у робочому GNOME ці служби вже запущені й відповідають миттєво. Виняток —
`org.freedesktop.secrets` (справжній `gnome-keyring-daemon` з тимчасовим HOME): без нього
OrcaSlicer 2.4.2 падає (SIGSEGV). Для оригіналів також `SSL_CERT_FILE` (інакше модальне
питання про сертифікати), `NO_AT_BRIDGE=1` і `WEBKIT_DISABLE_DMABUF_RENDERER=1` (з DMABUF-рендером
WebKitGTK Orca 2.4.2 у headless mutter зависає на створенні головного вікна).

**Фікстури** (`tools/bench/fixture_3mf.py`, детерміновані, генеруються щоразу):
- `small.3mf` — 1 пластина, UV-сфера 20 000 △ (r 20 мм), 125 КБ;
- `heavy.3mf` — 4 пластини по UV-сфері 250 000 △ (r 30 мм), разом 1 000 000 △, 7 МБ.

Формат як у Bambu Studio (пластини в `model_settings.config`, сітка з кроком 307,2 мм) з
`project_settings.config`, розгорнутим по `inherits` із профілів BBL рушія. Без нього Orca CLI
2.4.2 падає після запису G-code; назв пластин немає навмисно (OrcaSlicer#7920).

**Сценарії.** Кожен прогін — новий процес; порядок застосунків чергується по колах, щоб дрейф
навантаження ділився між ними. Перед статистикою — один розігрівальний запуск кожного
застосунку (копіювання системних профілів тощо). Кеш сторінок теплий (`drop_caches` потребує
root), тобто «холодний старт» = новий процес на теплому диску з підготовленим профілем.
1. `start` ×5: запуск без файлу → перше вікно → **головне вікно** (≥900×550, без сплеш-екрана)
   → **готовий** → 10 с простою.
2. `open-small`, `open-heavy` ×3: запуск із 3MF в аргументі → готовий → 5 с простою → орбіта
   (100 кроків миші по 4×1 px через 20 мс з порожнього місця над столом) → зум (20 кліків
   колеса) → **Ctrl+R** (нарізка пластини 1 у всіх трьох) → готовий Preview → 3 с простою →
   орбіта над траєкторією.
3. `cli-small`, `cli-heavy` ×5: прямий виклик рушія як у Slicenv (`--debug 2 --load-settings
   machine.json;process.json --load-filaments filament.json --load-defaultfila --orient 0
   --arrange 0 --slice 1 --export-3mf`, ті самі JSON, які Slicenv записав у свій кеш нарізки) —
   нижня межа часу нарізки в Slicenv.

**«Готовий»** — однаково для всіх: головне вікно є, і CPU усього дерева процесів нижче 15 % одного
ядра протягом 1,5 с (для нарізки — 2 с після сплеску >60 %); момент — початок цього тихого вікна.
Для Slicenv додатково записані маркери зі stderr: перший кадр в’юпорта (`UI_TRACE`), модель
завантажена (`object_count`), рушій готовий (`engine_loading=false`), `slice::background`
(спан фонової задачі = підготовка входу + процес рушія), шари в Preview (`layers` ≠ null).

**Метрики** (`/proc` кожні 100 мс по всьому дереву, разом із процесом рушія й WebKit-процесами):
CPU = Σ(utime+stime) живих і завершених процесів (втрата ≤100 мс на процес); RSS = Σ VmRSS
(спільні сторінки рахуються кілька разів); PSS = Σ `smaps_rollup` (кожні 0,5 с; чесніша сума
для багатопроцесних оригіналів); GPU — `/proc/<pid>/fdinfo` amdgpu, дедуп за `drm-client-id`:
`drm-memory-vram`/`drm-memory-gtt` (на 780M «VRAM» — це UMA-виділення з RAM), зайнятість =
Δ`drm-engine-gfx`/Δt. Окремо — GPU композитора (mutter + Xwayland), бо через нього йде
презентація всіх вікон. Для CLI — ще `wait4` rusage (точний CPU і maxrss процесу).

**Причина хвоста** — дві вкладені рамки вікна: `Root` з gpui-component 0.8 сам загортає вміст у
`window_border()` з тінню 20 px, а `Workspace` — ще раз, з тінню 0. Кожен кадр
`set_client_inset` перемикався 20 → 0; на X11 це `_GTK_FRAME_EXTENTS`, mutter двічі
переконфігуровував вікно (1600×980 ↔ 1560×940), а GPUI на кожен `ConfigureNotify` робить
`bounds_changed` → `refresh()`: ще один повний кадр, ще й зі скинутим кешем видів. Друге джерело —
очікування readback через `request_animation_frame` (кадр вікна на кожен тік, поки GPU читає
пікселі). Знайдено діагностичною збіркою gpui-pre з бектрейсами в `invalidate_view`/`refresh`.

окремий вид, який орбіта/зум/панорама сповіщають замість усього `Workspace`; на кадрі орбіти
`objects::panel` і `preset_editor::render` більше не викликаються; (б) кадр GPU чекає фоновий
потік, а не цикл перемальовок; (в) частоту кадрів і далі обмежує цикл GPUI (X11 — таймер
частоти режиму RandR, Wayland — frame callbacks), 3D-кадр подається лише з paint, не частіше
за кадр вікна: під потоком ~375 подій миші/с — 15 3D-кадрів за 0,65 с. Readback через CPU
лишився (див. нижче), тому GPU орбіти досі вищий, ніж у Bambu.

### Що не зроблено й чому

- **Показ 3D без readback через CPU.** У gpui-pre 0.3.10 немає публічного шляху: `PaintSurface`
  є лише на macOS (CVPixelBuffer), атлас і `wgpu::Device` вікна приватні, а рендерер в’юпорта
  живе на окремому пристрої wgpu — спільна текстура вимагала б external memory (dmabuf) між
  двома пристроями або форку gpui-pre-wgpu з новим примітивом сцени. Окреме дочірнє вікно чи
  subsurface поверх Wayland/X11 ламає порядок оверлеїв (куб, панелі інструментів, меню над
  сценою). Readback і так асинхронний (кадр чекає фоновий потік, UI не блокується), а знижену
  роздільність під час руху автори вже відкидали через розмиття — тож лишено як є: CPU орбіти
  тепер на рівні Bambu, GPU — у 2–4 рази вищий.
- **Потоковий/паралельний розбір G-code і перші шари до кінця розбору** — розбір пластини
  займає 16–29 мс, побудова буферів (вже у фоні) — 13–17 мс; виграш не вартий ускладнення.
- **Ледаче створення рендерера в’юпорта** — після `MemoryUsage` порожній пристрій тримає кілька
  МБ, а `Renderer` використовується в ~60 місцях як не-`Option`.
- **Поле 20 px навколо вікна.** Коміт 69f3191 прибрав gutter під тінь, але `Root` gpui-component
  0.8 однаково додає власну рамку з тінню 20 px (так було й до цих змін). Прибрати її можна
  лише форком/патчем gpui-component.
- **Нативний Wayland** не вимірювався (стенд керує вводом через X11). Петля `ConfigureNotify` —
  шлях X11, але у Wayland-бекенді gpui кожна зміна `set_client_inset` робить `update_window`
  (геометрія вікна) і `request_redraw()`, тож подвійна рамка й там щокадру міняла геометрію й
  просила новий кадр; після виправлення значення стале.

## Висновки

1. **Старт і відкриття — у рази швидше й легше.** Головне вікно за 0,2 с проти 1,4–1,6 с
   (Bambu) і 0,8–4 с (Orca); CPU старту 0,2–0,3 с проти 2–4 с. У простої Slicenv тримає
   82–88 МБ PSS проти 760–970 МБ в оригіналів (у тих — wxWidgets + WebKit + усі вендорні
   профілі в пам’яті). 1 М △ heavy: модель на екрані за 1,1 с і 270–280 МБ PSS, Bambu Studio —
   готовий лише за 10 с, 15–17 с CPU і 1,3 ГБ PSS. Простій із моделлю: Slicenv 0–4 % ядра,
   Bambu 16–18 % (оригінал не засинає з heavy-сценою).

2. **Орбіта й зум — у 3–4 рази дорожчі за CPU і GPU.** Slicenv: ≈47 % ядра і 33–42 % GPU плюс
   ≈9 % GPU композитора; Bambu Studio на тій самій сцені: 11–16 % CPU, 5–9 % GPU, 2 % композитора.
   Причина в архітектурі кадру: 3D малюється офскрін у wgpu, кадр читається назад
   (`poll_readback`/`install_frame`) і подається в GPUI як зображення (`paint_image`), а GPUI
   перебудовує й презентує все вікно (`Workspace::render` щокадру). Оригінал малює GL-полотно
   прямо у своє вікно. Плавності це не шкодить (за `tools/bench/gui-bench.sh` кадр орбіти
   ≈3 мс, `bench/baselines.json`), але енерговитрати на ноутбуці помітні.

3. **Хвіст перемальовок після вводу.** Одна подія вказівника (навіть рух миші за межі вікна)
   запускає ≈1,5–2 с безперервних повних перемальовок інтерфейсу при ≈50 % ядра. 3D-кадр при
   цьому не подається (у профілі є `Workspace::render`/`viewport::paint_image`, немає
   `viewport::submit`). Після серії подій (орбіта, зум, нарізка) хвости зливаються в плато
   на 5–12 с; звідси великий розкид «готовий» і «до тиші CPU» у Slicenv. Ймовірні джерела:
   `InputRateTracker` у gpui (1 с «тримати презентацію» після вводу ≥60 подій/с) і щось, що
   робить вікно брудним щокадру. Це варто дослідити першим: простій має бути 0 %.

4. **Нарізка = час рушія + накладні витрати процесу + Preview.** Сам рушій CLI: 0,65–0,69 с
   (small) і 3,5 с (heavy) стіни, ~10,5 с CPU. `slice::background` у Slicenv = CLI + 0,1 с
   (small) / +1,1 с (heavy): знімок проєкту в 3MF на 1 М △ і прогрів. Далі **завантаження
   Preview — найбільший внесок**: +2,5 с (small) і +5,3 с (heavy) до появи шарів. Разом від
   Ctrl+R до шарів 3,3 с / 9,9 с проти 0,45 с / 0,84 с у Bambu Studio, яке ріже в тому самому
   процесі: модель і конфіг уже в пам’яті, немає запуску процесу, завантаження всіх вендорних
   профілів, розбору й запису всього 4-пластинного 3MF (`--export-3mf` пише 23 МБ з усіма
   об’єктами). Зате пік пам’яті нарізки в Slicenv (з рушієм) — 620–630 МБ проти 1,36 ГБ.

5. **GPU-пам’ять.** Slicenv виділяє 276 МБ VRAM навіть на сторінці Home без 3D-сцени
   (у Bambu — 134–190 МБ із порожнім столом); з heavy-сценою 341 МБ, у Preview heavy 620–640 МБ
   проти 360 МБ у Bambu. GTT 21–110 МБ.

6. **Знахідка коректності (поза бенчем): Slicenv + рушій Bambu 2.7 — виправлено.** Прямий
   Bambu 2.7 CLI на `small.3mf` лише з `project_settings` дає 11,4 г / 24 хв; з
   `machine.json`+`process.json`, які записав Slicenv, — 486 г / 1 год 41 хв. Причина:
   `PresetStore` зводив профілі всіх вендорів в одну мапу за іменем, і службові батьки
   (`fdm_machine_common`, `fdm_process_common`, `fdm_filament_*`) брались від вендора, якого
   останнім віддав `read_dir`, — тут Anker. Звідти `use_relative_e_distances = 0` і
   `G92 E0` у `before_layer_change_gcode` (у BBL цього ключа немає, дефолт рушія — 1): G-code
   з абсолютним E, а вага рахується як для відносного (×140), плюс 3 стінки, cubic, 4 нижні
   шари, `skirt_loops = 2`. Orca 2.4.2 / 2.5 мали ту саму ваду в менших масштабах (line_width
   0,45, 3 стінки, 210 °C; час +10…50 %). Тепер батька шукаємо у своєму вендорі, далі в
   OrcaFilamentLibrary — як `PresetBundle` рушія; ключі, які старий Slicenv встиг записати в
   project_settings проєктів, при нарізці й відкритті не стають правками. Регресія:
   `crates/slicer/tests/engine_presets.rs` (вага й час ±5 % до еталона, CONFIG_BLOCK = пресети)
   на кожному встановленому рушії. Рядки `slicenv+bambu-2.7` у таблицях вище зняті до
   виправлення: G-code там значно більший, тож час Preview завищений.

## Що варто оптимізувати (за вимірами)

1. ✅ **Хвіст перемальовок після вводу (висновок 3)** — див. «Після оптимізацій». Зняти `SLICENV_PROFILE_ALL` у простої
   після одного руху миші й знайти, хто робить вікно брудним (hover-стан, `cx.notify()` з
   рендера, gpui `InputRateTracker`). Ціль: 0 % CPU через ≤100 мс після останньої події.
2. ◑ **Шлях кадру в’юпорта (висновок 2)** — панелі кешуються; readback лишився. Не перебудовувати весь `Workspace` під час орбіти:
   кешувати панелі (`settings::rules`, `preset_editor::render`, `objects::panel` — кожен кадр),
   оновлювати лише в’юпорт. Далі — прибрати readback: показувати wgpu-текстуру напряму
   (спільна текстура з рендерером gpui), а не копію через CPU.
3. ✅ **Preview після нарізки (висновок 4).** Додати spans на розбір G-code і завантаження
   геометрії Preview (зараз їх немає, видно лише сумарні 2,5–5,3 с), розбирати G-code
   потоково/паралельно, поки рушій ще пише, і показувати перші шари до кінця розбору.
4. ◑ **Вхід рушія** — лише об’єкти пластини; `--export-3mf` Orca і раніше писала лише їх. Передавати в CLI лише об’єкти пластини, що ріжеться (heavy: 250 тис. △
   замість 1 М), і не просити `--export-3mf` з усією моделлю, якщо Slicenv однаково збирає
   `.gcode.3mf` сам; це зріже ~1–2 с із 3,5 с CLI на важких проєктах.
5. **Тримати рушій «теплим».** Головна різниця з Bambu GUI — запуск процесу й завантаження
   профілів щоразу. Варіант — фоновий процес рушія з `--pipe`, що чекає наступного завдання
   (якщо CLI це дозволяє), або хоча б кеш розгорнутих профілів.
6. ✅ **VRAM на Home** (висновок 5) — `MemoryHints::MemoryUsage`: не створювати цілі рендеру 3D, поки сцени немає.
7. **Пресети для рушія Bambu** (висновок 6): розгортати `inherits` повністю перед
   `--load-settings`; додати тест «вага G-code CLI ≈ вага з GUI» на маленькій фікстурі.

## Що не виміряно і чому

- **OrcaSlicer GUI: відкриття, нарізка, GPU.** У headless mutter Orca 2.4.2 після появи
  вікна блокує головний потік (чорне 3D-полотно, Ctrl+R відпрацьовує через ~12 с). Без
  Secret Service вона падає з SIGSEGV, із gnome-keyring полотно лишається чорним; у 2.5.0-beta
  був SIGSEGV під час орбіти. Bambu Studio з того самого коду працює повністю. Тому для Orca —
  лише старт (з позначкою ⚠ для 2.4.2), а рушій Orca порівнюється через `slicenv+orca` і
  прямий CLI. Спробувати знову: `compare.py --orca-gui`.
- **Справжній холодний диск** (`echo 3 > /proc/sys/vm/drop_caches` потребує root) і перший
  запуск на чистому профілі (розігрівальні запуски не входять у статистику, але лежать у JSON
  з `warmup: true`).
- **Нативний Wayland Slicenv.** Усі застосунки — X11-клієнти Xwayland, щоб одним `xdotool`
  керувати всіма. На робочому столі Slicenv іде нативним Wayland: витрати композитора й
  хвіст перемальовок там можуть відрізнятися.
- **Час кадру оригіналів.** У Bambu/Orca немає маркера кадру, тож «готовий» для них —
  лише через тишу CPU; для Slicenv є маркери, і обидва числа наведені.
- **Мережа** не ізольована (`unshare -n` ламає FUSE-монтування AppImage 2.8); входу в хмару
  немає, перевірки оновлень оригіналів могли звертатись до мережі.
- **Точність:** CPU ±10 мс тіків на процес і ±100 мс на процес, що завершився між семплами;
  PSS і GPU — кожні 0,5 с, тож короткі піки (<0,5 с) у них можуть не потрапити (через це в
  JSON у Slicenv «PSS старту пік» ≈1 МБ: старт коротший за інтервал); RSS — сума по процесах
  (спільні сторінки рахуються кілька разів, тому для порівняння беріть PSS).

## Відтворення

```bash

tools/bench/compare.sh                    # повний прогін, ~30–40 хв + очікування load < 8
tools/bench/compare.sh --quick            # по одному прогону — перевірити, що стенд працює
```

Корисні прапорці `compare.py`: `--shots` (знімки вікна в першому прогоні: `ready.png`,
`after-orbit.png`, `sliced.png`, `preview-orbit.png`), `--keep`/`--work` (лишити логи й

### Windows (hometop) — як повторити вручну

`compare.py` прив’язаний до Linux (`/proc`, mutter, xdotool) і на Windows не запуститься.
Переносні частини:
- фікстури: `python fixture_3mf.py heavy heavy.3mf --profiles "<рушій>\resources\profiles"`;
- **CLI-нижня межа**: `Measure-Command { & "C:\Program Files\OrcaSlicer\orca-slicer.exe" --allow-newer-file --load-settings "machine.json;process.json" --load-filaments filament.json --load-defaultfila --orient 0 --arrange 0 --slice 1 --outputdir out heavy.3mf }`
  (JSON узяти з `%LOCALAPPDATA%\slicenv\cache\sliced\…` після нарізки в Slicenv; Orca 2.3.0
  за `docs/PORTING.md` встановлена в `%ProgramFiles%\OrcaSlicer`, портативну 2.5.0 — шлях,
  куди її розпаковано; для 2.3.0 на 3MF з назвами пластин CLI падає — фікстура їх не має);
- **старт і пам’ять GUI**: `Start-Process` + цикл `Get-Process -Id … | Select WorkingSet64, PrivateMemorySize64, CPU`
  і `(Get-Process).MainWindowHandle -ne 0` як «вікно з’явилось»;
- **GPU**: `Get-Counter '\GPU Engine(pid_<PID>*engtype_3D)\Utilization Percentage'` і
  `'\GPU Process Memory(pid_<PID>*)\Dedicated Usage'`;
- запуск через `ssh hometop` — без інтерактивного робочого столу GUI не матиме вікна; GUI-частину
  виконувати в сесії користувача (Планувальник завдань з «Run only when user is logged on»).

Ці кроки не запускались: на hometop у цей час працював інший агент.
